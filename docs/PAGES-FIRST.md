# RECORD v0.78：GitHub Pagesで使える公式確認済み目次

2026-10-27の方針変更。新しい外部登録・検索API・サーバー・DBを公開の必須条件にせず、既存GitHub Pagesで動く目次を優先する。PR #23の公式発売確認・共通取得アダプター・任意APIのコードを残し、公開経路だけを明確に分ける。

## 利用者の操作

1. 日本語・英語のアーティスト名を入力するか、対応アーティストのボタンを選ぶ。
2. 同じPagesサイトの`data/official-catalog.json`を一度読み、名義・別名を照合する。
3. 正規発売確認済みの作品だけを表示。作品ごとに公式の根拠URL、資料確認日、レーベルを確認できる。
4. 「YouTube Musicで探す」で作品名とアーティスト名の検索を開く。配信先を検証済みと扱ったり、別作品へ自動転送したりしない。

公開目次は既存の確認済み **5組・56作品** をそのまま使用する。

| アーティスト | 確認済み作品数 |
| --- | ---: |
| Norah Jones | 12 |
| Miles Davis | 34 |
| Bill Frisell | 4 |
| Cannonball Adderley | 1 |
| Ambrose Akinmusire | 5 |

これは全ディスコグラフィーや対応アーティスト全体を網羅する主張ではない。ジミ・ヘンドリックスなど、任意APIで取得できたことがある名義でも、静的な公開目次に入っていなければ今回は未対応として扱う。登録数を増やすために未確認情報を混ぜない。

## 表示・根拠の条件

公開検索は`searchRecord`→`searchPublishedCatalog`→既存`confirmedCatalogAlbums`/`renderOfficialCatalog`を利用する。公式サイトへのリアルタイム通信や、MusicBrainzによる正規発売認定を行わない。ブラウザの保存記録が新しい作品の発売根拠に昇格することもない。

作品の公式確認フラグだけでなく、作品単位の確認、公式許可ホストのHTTPS URL、レーベル、資料確認日、確認内容を必要とする。共通アダプター生成分は名義ID・ルール・出典URL・資料SHA-256・発売済み日付/過去年も照合する。公式ドメインへの単なるリンクでは生成分を認めない。既存の手動確認分は従来の確認資料を維持する。

静的目次は公開前に確認したスナップショットであり、検索時に再確認したとは表示しない。APIの24時間キャッシュ期限と静的目次の資料確認日を混同しない。歴史的な正式発売の確認を保存し、後日の公式サイトの掲載継続やYouTube Musicの配信継続まで保証しない。

今回、公式目次の作品情報は変更していない。PR #20までの個別確認と、その後の公式資料を使った共通生成で確認した56作品を再利用する。取得困難な情報源へ再接続を強要せず、資料不足の新規候補は掲載しない。

## 状態の区別

- `catalog_ready`：対応範囲と公開作品数を案内。
- `catalog_confirmed`：公開中の公式確認済み目次に該当する作品を表示。
- `catalog_unsupported`：公開中の目次で確認できない。未対応の可能性を表示し、サイト/作品の不存在は断定しない。前の検索の作品は消す。
- `catalog_error`：JSON取得失敗・形式不正。通信エラーとして案内し、再読み込みボタンを出す。未対応や作品なしとは区別する。

公式サイトへのアクセス失敗は、この静的検索では発生しない。目次更新時の取得失敗は更新レポートへ残し、既存の確認済み作品を壊さず更新を保留する。公式サイトのアクセス制限を回避する機能は追加しない。

## 更新方法と負荷

既存`generate_official_catalog.py`と公式レビュー処理を利用できる。担当者が必要なときだけ公式資料を取得し、別ファイルに生成→根拠と差分を確認→テスト→更新PR→マージの順にする。`official-discography.yml`は手動プレビューのまま、mainへの自動追加・自動公開をしない。作品ごとの手入力だけに依存せず、対応するBlue Note/Warner等の共通アダプターを再利用できる。

利用者の検索はPages内のJSONだけを使うため、利用者数や検索回数が増えても公式サイトへの取得回数は増えない。目次JSONは同一ページ内で再利用する。API用の日次HTTP予算やDBは、この公開方式には不要。

## 将来のAPIを追加する境界

`record-search-mode`メタタグの既定値は`catalog`。`record-api-base`が入っていても、モードを明示的に`api`へ変えない限りAPI検索へ進まない。`scripts/configure_public_api.py`は将来の承認済みAPI URLと`api`モードを両方設定する。現行Pagesの値は変更しない。

`server/`、`data/official-realtime.json`、PostgreSQL/SQLite保存、CORS、流量制御、Dockerfile、render.yaml、APIのテストは残す。Render/Neonを登録・作成せず、APIチェック用のDocker/PostgreSQL結合テストは`optional-api-tests.yml`の手動実行に移す。通常CIと公開には外部アカウントもAPIホストも不要。

APIモードの障害から静的目次へ黙って切り替えることはしない。将来モードを切り替える際には、その方式に対応する説明・表示条件・テストを一緒に確認する。
