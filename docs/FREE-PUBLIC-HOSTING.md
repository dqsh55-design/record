# RECORD 無料優先の一般公開構成

2026-10-27調査。価格は税別USD、為替換算なし。無料枠は変更されるため、登録画面で再確認する。本書は構成提案と実装済みの準備であり、本番サービスを作成・公開した記録ではない。

## 推奨

小規模の一般公開ベータは **既存GitHub Pages（画面）＋Render Free（Python API 1台）＋Neon Free（PostgreSQL）**。月額目標は$0。独自ドメイン、有料プラン、常時起動、追加サービスは不要。利用上限で停止してよいことを前提にし、稼働率の保証はしない。Render自身もFreeを本番用途には推奨していないため、無停止の正式サービスとは分けて扱う。

ブラウザはPagesからHTMLを読み、HTTPSのAPIへアーティスト名だけを送る。APIが公式情報を取得して発売を判定し、Neonへ作品名・公式URL・根拠ハッシュ・確認日時を保存する。既存の利用者の保存記録は引き続きブラウザ内に置く。Neonをブラウザに直接公開せず、接続情報はRenderの秘密環境変数のみへ設定する。MusicBrainzや事前目次へのフォールバックは追加しない。

GitHub Pagesは公開リポジトリで利用でき、サイト1GB、帯域100GB/月（soft limit）等の制限がある。静的画面の配信に残し、API実行やDB保存には使わない。商用サービスへ発展させる場合はPagesの利用条件も再評価する。

Neonの古い記事には0.5GB等の記述があるが、今回取得した公式料金・プランページは1GBと記載。Renderの古い記事の100GB無料帯域ではなく、現行Hobbyの5GBで見積もる。

## PR #22の確認と今回の変更

#22は公式発行元のホスト制限、名義・アルバム区分・発売済み日付の検証、24時間の作品単位の証拠期限、未確認/アクセス制限/取得失敗の区別を既に備える。一方、そのままでは同一オリジン前提で、SQLite保存はRender Freeの再起動に耐えず、一般公開時の流量制御も不足する。

今回追加した準備:

- `RECORD_DATABASE_URL`でPostgreSQLへ切り替え、SQLiteと同じ判定・保存・マージ規則を共用。接続ごとにトランザクションを閉じ、アイドル接続プールを保持しない。TLS必須、接続・SQLタイムアウトを設定。DB障害時は503を返し、未確認情報や消えるローカルDBへ切り替えない。
- 本番テンプレートは永続DB未設定なら起動を拒否。`/health`はプロセス確認のみでDBを起こさない。永続保存の確認は実検索で行う。
- CORSはPagesの完全一致オリジンだけを許可。ワイルドカード、認証Cookie、公開APIキーなし。CORSはブラウザの読み取り制御であり、bot対策や認証ではない。同一GitHub Pagesオリジン配下の別プロジェクトも許可範囲になる。
- APIはプロセス全体60件/分、超過は429＋Retry-After。IP・検索履歴の独自アクセスログやIP識別用DBは追加しない。偽装Forwardedヘッダーには依存しない。1ワーカー構成で使い、複数ワーカー/複数台への変更前に共有流量制御を導入する。
- 公式ホストごとに同時HTTP1件、開始間隔1秒以上、HTMLメモリ保存60秒（最大32ページ、計400万文字）。既存の4検索同時上限、同一検索の進行中処理の共有、応答5MB上限を維持。
- 実HTTPは全ホスト合計2000回/UTC日まで（転送も計上）、使用数はDBで原子的に更新して再起動後も保持。超過は診断に「本日の公式サイト取得上限」、作品がなければ取得失敗として表示する。DBに予算を確保できなければ取得しない。
- 発売確認済み作品は24時間再利用。手動再確認は成功/失敗後300秒の間隔を設け、失敗しても証拠期限を延長しない。根拠不足/取得失敗の結果もメモリ内で300秒再利用するが、作品を確認済みとしてDB保存しない。メモリ制限は再起動でリセットされ、日次HTTP予算はリセットされない。
- 画面の待機上限180秒、15秒後に起動・確認待ちの案内。自動リトライ、稼働維持のための定期pingは行わない。
- 既存の公式一覧探索で、最後に走査した別アーティスト名が別名一覧へ混入する問題を修正。一致したリンクの名義だけを採用する。

1秒間隔はこの単一APIプロセス内の制御。ローリング更新中に旧新プロセスが重なる場合のホスト間隔までは保証しない。日次予算だけは共有DBで制御する。再配置・リージョン変更・IP変更をアクセス制限の回避目的に使わない。

## 費用とアクセス負荷の見積もり

初回検索は最大で公式一覧3、作品一覧8、ジミの詳細6程度の取得があり、転送・再試行なしでも最大17回になる。2000回/日は最大構成の未キャッシュ検索で約117回相当。これは対応可能な利用者数やSLAを示す数値ではなく、公式サイトへの負荷の安全上限。失敗やページ構造で回数は変わる。

API JSONを1回50KBと仮定すると1万レスポンスで約0.5GB。DBへの通信・TLS・プロトコル分もRenderの外向きに加わるため、5GBを全てブラウザ向けに使えるわけではない。公式HTMLはAPIの受信だが、その取得要求・DB転送などサービス起点通信も帯域・停止判定の対象になる。Renderは外部サービスへの通信が多い無料APIを停止する場合がある。

Neonは小さなクエリでも休止までの5分がCU使用量に関係する。0.25 CUで毎日約13時間以上起きていると100 CU時間/月に近づく。キャッシュヒットにもDB接続は必要なので、利用者が分散して継続アクセスすると無料枠が先に尽きる場合がある。初期は最小0.25 CU、上限も可能なら0.25 CUに固定し、1プロジェクト/1ブランチだけ使う。

無料枠は将来の無償継続を保証しない。Renderは支払い方法未登録なら帯域超過で停止、ビルド枠超過で新規ビルド停止。Neon FreeはCU/転送上限で停止し、保存上限では書き込み失敗。有料移行は別途承認してから行う。カード必須・初期課金が表示されたらその場で登録を止め、再検討する。

## 公開前の実施手順

1. **外部登録の承認後のみ**Render Hobby/FreeとNeon Freeを作成する。カードなしで進める範囲を優先し、支払い方法・有料契約・独自ドメインを追加しない。GitHub連携の対象はこのリポジトリだけにする。
2. NeonはRenderに近い利用可能なリージョンで作成。接続URLはRenderの秘密変数`RECORD_DATABASE_URL`へ設定し、`sslmode=require`以上を付ける（Neon推奨のpooler URL/セキュリティオプションを使用）。URLをHTML、GitHub変数、PR、ログに貼らない。
3. `render.yaml`を使い`plan: free`の単一Dockerサービスだけを作成する。`RECORD_REQUIRE_DATABASE=1`、`RECORD_ALLOWED_ORIGINS=https://dqsh55-design.github.io`。自動デプロイは無効。無料サービスであることを画面で確認して手動デプロイする。
4. `/health`を確認後、3名義を空の本番DBで検索し、確認済み作品・公式リンク・失敗区別・許可/拒否CORSを確認する。再配置後も保存結果が再利用できること、無料枠の使用量を確認する。公開先のネットワークから公式サイトにアクセスできるかはローカル/CIだけでは保証できない。robots.txt・利用条件が自動取得を禁止する情報源は停止し、制限は回避しない。
5. APIが使えることを確認してから、`python scripts/configure_public_api.py https://実際のAPIホスト --output index.html`でPagesのAPI先を設定する。この差分をレビューし、UIとAPIの同じ版を公開する。URL未定の現在はメタタグを空のままとし、既存Pagesへ未接続UIを公開しない。
6. スマートフォン幅で3名義、保存再利用、API休止後の起動待ち、429、API停止時の案内、既存記録の保持を確認する。DB接続情報が公開物に入っていないことを確認する。
7. 初週はダッシュボードでCU時間・転送・DB容量・HTTP予算・403/429を確認する。利用量70%を目安に状況を確認し、停止を受け入れるか有料化を相談する。アラートは手動設定するもので、このPRでは登録・スケジュール作成を行っていない。

不具合時はPagesを直前の版に戻し、APIは停止できる。NeonのDBを削除せず、機密URLが漏れたら認証情報を更新する。無料枠の復旧履歴は短いため、長期運用前に手動`pg_dump`等のバックアップ運用を決める。共通DBの作品情報は公式ページから再確認可能だが、バックアップがあるとは扱わない。
