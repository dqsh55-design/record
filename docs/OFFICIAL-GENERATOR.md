# 公式発売情報からの共通目次生成（v0.76）

> v0.77では検索時取得・SQLite保存を主経路に変更。以下は従来方式の参考資料です。[現在の設計](ON-DEMAND-SEARCH.md) を参照してください。

従来の「候補を保存し、作品ごとのレビューJSONを手入力する」処理に加え、承認済みの情報源・抽出ルールで根拠が揃った作品から目次を生成する経路を実装。MusicBrainzへのHTTP通信・作品登録APIは使用しない。新規名義のIDはRECORD独自ID。

## 流れ

1. `data/official-generation.json` に承認済み情報源・プロバイダー共通ルールを定義。
2. Blue Noteの公式アーティスト一覧から新しい名義を発見（新規ページは1実行2名義まで）。同じホスト・artistパス・見出し内の名義リンクのみ採用。既存の手動確認名義は明示した情報源を維持。
3. 公式アーティストページから作品を抽出。名義一致・アルバム区分・発売済みの情報を検証。
4. 既存目次へ追加。既存の根拠・年・ID・保存記録は更新・削除しない。再発の形式違いと同名重複をまとめる。
5. 出典URL、取得ページのSHA-256、適用ルール、名義ID、発売済みを示す原資料の値を作品に付与。
6. 生成物をテストし、差分があれば更新PRを作成。マージ後に公開反映。

アーティスト一覧からの発見と作品の認定は別。公式ドメイン内のリンクであるだけでは認定しない。Blue Noteの新規名義には作品ごとの登録やアーティスト個別設定が不要。Warnerは既存の本人公式ディスコグラフィーURLの設定を共通処理で使用する。Sonyや任意の公式サイトの全HTML形式・全アーティストを自動発見する完成形ではない。

## 確認ルール

| 共通アダプター | 必須の資料情報 | 情報が足りない場合 |
|---|---|---|
| Blue Note | 承認したホスト、本人h1、release-entry、本人ページへの名義リンク1件、過去年の発売年 | ゲスト・バンドとの複合名義、年なし、当年・未来年は保留 |
| Warner Japan | 承認したホスト、本人見出し、ALBUMカード、本人ディスコグラフィー内の商品URL、有効な発売日≦当日 | 映像・別名義・不正日・未来発売日・別ホストは保留 |
| 汎用MusicAlbum JSON-LD | 承認したホスト、MusicAlbum、本人byArtist、AlbumRelease、MusicRelease、発行レーベル、有効な発売日、承認パスの根拠URL | 単なるリンク・曲・シングル・参照未解決・複数名義・レーベルなし等は保留 |

自動生成では初回発売年を推測せずyear=null。原資料の発売日・掲載年はgenerationProof内に保存し、再発日を初回年として使わない。Blue Noteの年だけでは当年の発売済みを証明できないため、当年分は一旦保留する。In My Dreamsもこの規則で保留。

Sony実サイトのJSON-LD適合は未確認。通常取得403の情報源は無効のままで通信しない。汎用アダプターはSchema.orgのMusicAlbum/MusicRelease形式をテストした拡張経路であり、現在のSonyページを取得できるという意味ではない。アーティスト公式サイトの新しいドメインを使う場合も、運営主体の確認とプロバイダー設定・ブラウザ許可ホストの変更をPRで行う。

## 実行

```sh
python scripts/generate_official_catalog.py
```

生成先は `reports/official-catalog.generated.json`、診断は `reports/official-generation.json`。入力目次・設定ファイルの直接上書き、生成先とレポートの同一路径を拒否する。取得・名義・構造のエラーは記録して非ゼロ終了し、既存目次を壊さない。生成物には他の健全な情報源の結果が含まれても、エラー時は定期ジョブが更新PR作成へ進まない。取得制限回避・非公開API探索は行わない。

## 定期更新

既存の公式収集ワークフローを共通生成へ接続。毎週月曜12:25 JST／手動実行でmainから生成・検証し、変更時だけ専用ブランチへコミットしてPRを作る。mainへの直接pushや自動マージは行わない。既に自動更新PRがある場合は重複PRを作らず、今回の生成物を成果物として残す。

GITHUB_TOKENによるPRでは通常のpull_request CIが起動しない場合があるため、matching-tests.ymlをworkflow_dispatchで明示実行する。PRのマージ前に、そのブランチの画面テストを含むCIの成功を確認する。定期ワークフローはcontents/pull-requests/actionsの書き込み権限を使用。リポジトリ側でActionsのPR作成が許可されている必要がある。マージ後の本番定期PR作成は未実行であり、成功を先取りして主張しない。

取得した外部文字列をシェルへ展開・実行しない。PR本文は固定のファイルから渡す。生成物と診断は90日間のActions成果物として保持。
